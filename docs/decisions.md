# Architektur- und Umsetzungsentscheidungen (V1)

Dieses Dokument schließt die Lücken, die bei der Prüfung von `CALENDAR_PLUGIN_CONCEPT.md` und `SPECIFICATIONS.md`
gefunden wurden, und protokolliert die offenen Punkte aus SPECIFICATIONS.md §20. Jede Entscheidung ist im Code
referenziert (`docs/decisions.md D-xx`).

| ID | Thema | Entscheidung |
|---|---|---|
| D-01 | Admin-UI | Vue 3 + Quasar SPA in `apps/admin` mit identischem Layout/Design-System wie sw-backupit (Entscheidung des Auftraggebers). Der Gutenberg-Block ist unabhängig davon und nutzt die WordPress-Block-API ohne Build-Schritt (`blocks/calendar/index.js`). |
| D-02 | Event-Status | Abweichend von der SQL-Skizze in SPEC §4.2 werden `confirmed` **und** `tentative` angezeigt; nur `cancelled` ist ausgeschlossen. Sonst würden vorläufige Termine (ICS `STATUS:TENTATIVE`, Google/M365 „tentative“) stillschweigend fehlen. |
| D-03 | Verzeichnis/Stil | SPEC-Struktur `src/{Domain,Application,Infrastructure,Presentation,Support}`. Framework-freier Code (Domain, Application, Support, Infrastructure/{Provider,Storage,Crypto,OAuth}) nach PSR-12/camelCase; alles mit WordPress-Aufrufen (Infrastructure/{Database,WordPress,Http}, Presentation, Bootstrap) nach WPCS. Siehe `phpcs.xml.dist` / `phpcs-wordpress.xml.dist`. |
| D-04 | Geschützte Views & Page-Cache | Views mit mindestens einer nicht-öffentlichen Quelle werden **nie** in das Seiten-HTML gerendert. Shortcode/Block geben einen Platzhalter aus; `assets/js/frontend.js` holt einen frischen REST-Nonce über `admin-ajax.php?action=sw_calendar_rest_nonce` (nie gecacht) und lädt `/views/{id}/render` (`private, no-store`). Ohne JavaScript erscheint ein Hinweis. HTTP-`public`-Caching nur, wenn die **ganze View** öffentlich ist. |
| D-05 | Monatsnavigation/Pagination | Zusätzliche Filterparameter `month` (`YYYY-MM`), `page`, `per_page`. Links ohne JS: `?swc_view={id}&swc_month=YYYY-MM`; mit JS: Neuladen über REST. |
| D-06 | Detailansicht | Auf derselben Seite: `?swc_view={id}&swc_event={occurrenceId}` (ACL- und View-Zugehörigkeit geprüft), mit JS als `<dialog>` über `/events/{id}?view={id}`. |
| D-07 | Platzhalter / Monatsraster | Vollständige Registry in `PlaceholderRegistry` (docs/templates.md). Das Monatsraster ist eine Plugin-Komponente (`calendar.events`); das Event-Template rendert jeden Eintrag einer Tageszelle. |
| D-08 | Ganztägige Termine | Als „floating dates“ gespeichert (`start_utc`/`end_utc` = Datum 00:00 „UTC“, Ende exklusiv). Die Abfrage vergleicht ganztägige Zeilen mit den lokalen Wanduhr-Grenzen der View-Zeitzone; dadurch verschieben abweichende Zeitzonen kein Datum. |
| D-09 | Private Einzeltermine | Quelloption `exclude_private_events`, **Default aus** (Entscheidung des Auftraggebers). Google `visibility=private/confidential`, M365 `sensitivity=private/confidential`, ICS `CLASS:PRIVATE/CONFIDENTIAL`. Wirkt nur als Sync-Filter, nie als ACL. |
| D-10 | Google Event-Typen | Default ausgeschlossen: `workingLocation`, `focusTime`, `outOfOffice` (persönliche Statuseinträge). Pro Quelle änderbar. |
| D-11 | Grenzwerte | Feed ≤ 10 MB (pro Verbindung 1–50), ≤ 20 000 VEVENTs, ≤ 3 660 Instanzen pro Serie im Fenster, ≤ 200 000 RRULE-Iterationen, ≤ 20 000 Occurrences pro Quelle, ≤ 1 000 Seiten pro Lauf, Lauf ≤ 240 s, Fenster je Richtung ≤ 1 095 Tage (`SW_CALENDAR_MAX_WINDOW_DAYS`), Datei ≤ 200 MB (Default 20), Quota 500 MB/Quelle und 2 048 MB global, REST-Rate-Limit 120/min/IP (0 = aus), Logs 30 Tage, Sync-Läufe 90 Tage (je Quelle min. 50 behalten), Gnadenfrist für widerrufene Dateien 24 h. Überschreitungen sind Fehler mit Code (keine heimliche Kürzung). |
| D-12 | Kategorien | Nicht in V1. `category` wird als `not_supported` abgewiesen (SPEC §20.8). |
| D-13 | Aufbewahrung | Occurrences außerhalb des Sync-Fensters werden beim nächsten erfolgreichen Sync entfernt; Provider-Items vergangener Einzeltermine (Google) werden nicht gespeichert. Ein vergrößertes Vergangenheitsfenster erzwingt einen Full-Sync. |
| D-14 | Recurrence | sabre/vobject (BSD-3) als RFC-5545-Engine. `EventIterator` ignoriert RRULE, sobald RDATE vorhanden ist; deshalb kombiniert `RecurrenceExpander` den `RRuleIterator` selbst mit DTSTART, RDATE, EXDATE und RECURRENCE-ID-Overrides. Identität: Serie + ursprünglicher Instanzstart (UTC bzw. Datum). |
| D-15 | Google Sync-Strategie | Referenzstrategie aus SPEC §6.1: `events.list` ohne `timeMin/timeMax`, `singleEvents=false`, `showDeleted=true`; Master und Ausnahmen werden in `swc_provider_items` gespiegelt und lokal expandiert; `410` → Full-Rebuild. Die zusätzliche Tabelle `swc_provider_items` (plus Staging `swc_sync_staging`) ist eine bewusste Ergänzung des Schemas. **Offen (SPEC §20.1):** Lastgrenzen sehr großer Kalender sind nicht gebenchmarkt. |
| D-16 | Microsoft 365 | Delegierte Berechtigungen eines Kontos, eigene App-Registrierung (Tenant, Client-ID, Client-Secret), Scopes `offline_access openid User.Read Calendars.Read`. `calendarView/delta` je Kalender; `nextLink`/`deltaLink` opak; Fenster im Cursor gebunden, Fensterwechsel → neuer Delta-Track. Ganztägige Termine werden bei einer Zeitzonenverschiebung auf das nächste Datum gerundet. Shared Mailboxes, Gruppenkalender, App-only: **nicht unterstützt** (Validierungsfehler `not_supported`). |
| D-17 | Public-only-Prüfung | Google Drive: `PUBLIC_VERIFIED` nur mit `anyone`-Permission; nicht lesbare Permissions → `UNKNOWN`. M365 `fileAttachment` → `PRIVATE`; `referenceAttachment`/`itemAttachment` → `UNSUPPORTED` (Freigabestatus von OneDrive/SharePoint wird in V1 nicht geprüft). ICS (URL und inline) → `UNKNOWN`. Damit synchronisiert `public_only=true` in V1 ausschließlich öffentlich geteilte Drive-Dateien. |
| D-18 | OAuth-Redirect | Feste Redirect-URI `/wp-json/sw-cloudcalendar/v1/oauth/callback`. Der Callback hängt den Code nur serverseitig an den einmaligen State (10 min) und leitet ins Admin; der Code-Tausch erfolgt in einem authentifizierten Admin-Request (Capability + REST-Nonce), gebunden an den Benutzer, der den Flow gestartet hat. Google-Tokens werden beim Trennen widerrufen; Microsoft bietet dafür keinen Endpunkt (Tokens werden lokal gelöscht). |
| D-19 | Secrets | XChaCha20-Poly1305 (libsodium) mit kontextgebundenen Associated Data (`connection:{id}`, `cursor:{sourceId}`). Schlüssel `SW_CALENDAR_ENCRYPTION_KEY` (Rotation über `SW_CALENDAR_ENCRYPTION_KEY_PREVIOUS`, Re-Encrypt beim Lesen); Fallback aus WP-Salts mit Warnung in der Diagnose. |
| D-20 | Protokollierung von Freigaben | Bestätigungen (Zeit, Benutzer, Quell-Revision) in den Source-Settings und in der Audit-Tabelle `swc_audit`. Bestätigungen können nur über die Flags `confirm_publication` / `confirm_private_attachments` erteilt werden. |
| D-21 | Dateispeicher | `SW_CALENDAR_PRIVATE_STORAGE_PATH` (empfohlen, außerhalb des Webroots) oder ein zufälliges Verzeichnis unter `uploads/` mit `.htaccess`/`web.config`, das nur nach erfolgreichem HTTP-Probe (Datei nicht abrufbar) akzeptiert wird; schlägt der Probe fehl (z. B. Loopback blockiert), bleibt der Anhangs-Sync gesperrt. ZIP-Dateien werden nie entpackt (kein ZIP-Bomb-Risiko serverseitig). Range-Requests nicht in V1. |
| D-22 | Cache | Template-AST und HTML-Cache in Transients, Schlüssel nach SPEC §11.3/§12 plus globalem Generationszähler (Leeren funktioniert auch mit persistentem Object-Cache). Alle Scopes von „Cache leeren“ leeren beide Caches. HTML-Cache nur für ausschließlich öffentliche autorisierte Quellen; TTL bis zur nächsten Tagesgrenze bzw. bis zum Ende des ersten angezeigten Termins (max. 15 min). |
| D-23 | Hintergrundjobs | WP-Cron alle 5 Minuten (`sw_calendar_cron_tick`, max. 25 s), täglich Wartung. Modus „system“: echter Cron mit `wp sw-cloudcalendar queue run`. Jobs werden atomar geleast; „Jetzt synchronisieren“ erzeugt nur einen Job. |
| D-24 | Multisite | Daten pro Site (`$wpdb->prefix`), Tabellen bei Netzwerkaktivierung je Site beim ersten Laden bzw. bei neuen Sites. |
| D-25 | Präfixe | Tabellen `{prefix}swc_*` (SPEC); Optionen, Transients, Hooks, AJAX-Actions `sw_calendar_*`; Konstanten `SW_CALENDAR_*`; CSS-Klassen `swc-`. |
| D-26 | Template-HTML und `unfiltered_html` | Templates werden unabhängig von `unfiltered_html` gegen die Allowlist des Compilers validiert (keine Skripte, Event-Handler, externen CSS-Ressourcen). Strenger als WordPress, damit auch Admin-Templates keine XSS-Verteiler werden. |
| D-27 | Tests | PHPUnit 11 (Unit/Integration ohne WordPress) und eine eigene WordPress-Testumgebung `tests/wp` (wp-phpunit, private MariaDB über `bin/test-db.sh`). Browser-E2E (`tests/E2E`, Playwright gegen eine Wegwerf-WordPress-Instanz) prüft Frontend-Verhalten, ACL im Browser und das Laden aller Admin-Seiten; die übrigen E2E-Szenarien aus SPEC §18.3 sind als WordPress-Integrationstests abgebildet (siehe `docs/testing.md`). |

## Offene Punkte aus SPEC §20 (nicht stillschweigend gelöst)

1. Google: Benchmark großer Kalender und dokumentierte Rebuild-Alternative fehlen (D-15).
2. M365: nur delegierter Zugriff eines Kontos; Shared Mailbox/Application Permissions offen (D-16).
3. Public-only: verlässliche Prüfung nur für Google Drive; OneDrive/SharePoint offen (D-17).
4. ICS-Paket: sabre/vobject 4.x, BSD-3-Clause, per Mozart isoliert (`SW\Calendar\Dependencies\Sabre\…`).
5. Frontend-Kalender: keine Fremdbibliothek; eigenes zugängliches Monatsraster (Tabelle) + Liste.
6. Dateispeicher: siehe D-21; Hosting-Ausnahmen müssen pro Installation in der Diagnose geprüft werden.
7. Attributplatzhalter: kontextsensitiver Parser (D-07, docs/templates.md).
8. Kategorien: nicht umgesetzt (D-12).
9. Consent-Screen/Verifikation bei Google (`drive.readonly` ist ein „restricted scope“) und Admin-Consent bei Entra ID müssen pro Installation geklärt werden.
